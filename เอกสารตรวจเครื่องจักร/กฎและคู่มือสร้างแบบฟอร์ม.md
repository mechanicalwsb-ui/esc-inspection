# กฎและคู่มือสร้างแบบฟอร์มเอกสารบันทึกจากไฟล์เดิม

จัดทำจากข้อกำหนดและการปรับปรุงในแชทนี้ เมื่อ 2 ตุลาคม 2569

เอกสารนี้ใช้เป็นแนวทางสร้างแบบฟอร์มใหม่จาก PDF หรือไฟล์เอกสารที่มีอยู่ โดยมีแบบฟอร์ม `FM-ML01-ML-02.html` เป็นตัวอย่าง ฟอร์มใหม่ต้องปรับรายการตรวจและบทบาทผู้เซ็นให้ตรงกับต้นฉบับ ไม่ใช้จำนวนช่องหรือช่วงค่าของเครื่องเทอร์ไบน์กับเครื่องอื่นโดยอัตโนมัติ

## 1. ขอบเขตและหลักการ

- เก็บต้นฉบับไว้เหมือนเดิม ห้ามแก้ไขหรือเขียนทับไฟล์ต้นฉบับ
- อ่านทั้งเนื้อหาและภาพเอกสารทุกหน้าที่เกี่ยวข้อง ก่อนสร้างแบบฟอร์ม
- แยกหน้ากรอกที่ใช้ง่ายออกจากรูปแบบเอกสารพิมพ์
- งานพิมพ์และ PDF ต้องตรงกับเทมเพลตต้นฉบับ ทั้งโลโก้ หัวเอกสาร กลุ่มหัวตาราง ค่าควบคุม หน่วย ลำดับช่อง และเส้นตาราง ยกเว้นส่วนลายเซ็นที่ออกแบบเพิ่มเติมตามข้อกำหนดนี้
- ข้อมูลที่ขาดหรืออ่านไม่ชัดต้องแจ้งให้ตรวจสอบ ห้ามเดาชื่อช่อง หน่วย หรือค่าควบคุม
- ไม่สร้างภาพหลักฐาน พิกัด GPS หรือลายเซ็นปลอมเพื่อให้แบบฟอร์มดูสมบูรณ์
- ปฏิบัติตาม `COLLABORATION_RULES.md` และอ่าน `CONTEXT.md` ก่อนแก้โปรเจกต์ ตรวจและประกาศล็อกใน `_lock/current.md` บันทึกงานใน `logs/` และปลดล็อกเมื่อเสร็จ

## 2. อ่านต้นฉบับและจัดทำรายการข้อมูล

ก่อนเขียนโค้ด ให้จัดทำรายการต่อไปนี้:

| รายการ | สิ่งที่ต้องตรวจ |
|---|---|
| เอกสาร | ชื่อ รหัสเอกสาร Revision วันที่ใช้ และขนาดกระดาษ |
| หัวฟอร์ม | วันที่ ปีการผลิต ฝ่าย แผนก และข้อมูลเครื่อง |
| ตาราง | ลำดับช่อง กลุ่มหัวตาราง ช่องรวม และหมายเหตุ |
| ค่าตรวจ | ชื่อค่า หน่วย ขอบเขตควบคุม และชนิดข้อมูล |
| รอบตรวจ | รายชั่วโมง รายกะ หรือรอบตามเอกสาร |
| ผู้เซ็น | ผู้บันทึก ผู้ตรวจทาน และผู้รับรอง |

แยกค่าตัวเลขออกจากข้อความและหมายเหตุ ระบุว่าช่องใดจำเป็นหรือไม่จำเป็น อย่าบังคับหมายเหตุทุกแถวหากไม่มีเหตุผิดปกติ

ตัวอย่างเครื่องเทอร์ไบน์ในแชทนี้มี 26 ค่าต่อชั่วโมง 24 ชั่วโมง รวม 624 ช่อง เริ่ม 07.00 น. จบ 06.00 น. วันถัดไป โดย 24.00 น. หมายถึงเที่ยงคืนวันถัดไป

## 3. หน้ากรอกข้อมูล

### 3.1 โครงสร้างหน้า

- หัวเว็บด้านซ้ายแสดงชื่อเอกสาร บริษัท รหัส และ Revision
- ด้านขวาของหัวเว็บรวมปุ่มเครื่องมือ ข้อมูลหัวฟอร์ม สถานะบันทึก และตัวเลือกเวลา
- หน้าจอเล็กจัดส่วนหัวเรียงลงมา ไม่บีบทุกช่องให้เล็ก
- เลือกเวลาเพื่อกรอกทีละชั่วโมง แบ่งช่องเป็นกลุ่ม เช่น ทั่วไป ความสั่นสะเทือน อุณหภูมิ และแรงดัน
- มีปุ่มก่อนหน้า ถัดไป บันทึกชั่วโมงนี้ และบันทึกแล้วไปชั่วโมงถัดไป
- มีตารางรวมสำหรับดูและแก้ไขทั้งวัน โดยค่าต้องตรงกับหน้ากรอกรายชั่วโมง
- เปลี่ยนชั่วโมงแล้วต้องไม่ทำข้อมูลหายหรือย้ายข้อมูลไปผิดชั่วโมง

### 3.2 สถานะปุ่มเวลา

| สถานะ | รูปแบบ |
|---|---|
| ยังไม่มีข้อมูล | สีเทา พร้อมข้อความ |
| กรอกบางส่วน | สีเหลือง พร้อมจำนวน เช่น 5/26 |
| กรอกครบ | สีเขียว พร้อมจำนวนครบ |
| เวลาที่เลือก | ขอบสีน้ำเงิน โดยไม่กลบสีสถานะ |

ถ้ามีเฉพาะหมายเหตุ ให้ถือว่ามีข้อมูลบางส่วน ไม่แสดงว่าไม่มีข้อมูล สถานะหลักฐานตรวจต้องแยกจากความครบของตัวเลข

### 3.3 ตัวเลขและค่าเริ่มต้น

- แสดงหน่วยและค่าควบคุมใกล้ช่องกรอก
- ค่านอกช่วงใช้สีแดงพร้อมข้อความ ไม่อาศัยสีอย่างเดียว
- ค่านอกช่วงที่เป็นตัวเลขถูกต้องไม่ควรถูกปฏิเสธ เพียงเพราะเครื่องทำงานผิดปกติ ควรบันทึกค่าจริงและคำอธิบาย
- ตรวจให้ถูกว่าเกณฑ์เป็น `<` หรือ `≤` และขอบเขตต่ำสุด/สูงสุดรวมค่าเส้นขอบหรือไม่
- ปีการผลิตกรอกครั้งเดียวแล้วจำเป็นค่าเริ่มต้น เปลี่ยนได้ และยังอยู่เมื่อเริ่มบันทึกใหม่
- ค่าเริ่มต้นแยกจากข้อมูลเอกสาร การนำเข้าเอกสารเก่าไม่ควรเปลี่ยนปีการผลิตเริ่มต้นโดยอัตโนมัติ

## 4. ฟอนต์ มือถือ และแท็บเล็ต

- ใช้ **Sarabun** สำหรับหน้าเว็บและข้อความที่สร้างในเอกสารพิมพ์/PDF
- เก็บไฟล์ฟอนต์ Regular และ Bold ในโฟลเดอร์โครงการ พร้อมใบอนุญาต เพื่อใช้งานออฟไลน์
- งานที่ใช้ภาพเทมเพลตต้นฉบับต้องคงตัวอักษรในภาพเดิม ส่วนข้อความข้อมูลที่เติมใช้ Sarabun
- ช่องกรอกบนมือถือใช้ขนาดตัวอักษรอย่างน้อย 16px และปุ่มหลักมีพื้นที่สัมผัสประมาณ 44px ขึ้นไป
- ตรวจมือถือ 360px และ 390px รวมถึงแท็บเล็ตแนวตั้ง/แนวนอน
- หน้าเว็บต้องไม่มีเนื้อหาล้นจอ ยกเว้นตารางรวมที่อนุญาตให้เลื่อนภายในพื้นที่ตาราง
- พื้นที่เซ็นรองรับนิ้ว ปากกา และเมาส์ ใช้ Pointer Events และป้องกันการเลื่อนหน้าเฉพาะบริเวณที่เขียนลายเซ็น

## 5. ลายเซ็นและลำดับรับรอง

### 5.1 เงื่อนไขก่อนเปิดหน้าเซ็น

- ข้อมูลหัวฟอร์มที่จำเป็นต้องครบ
- ตัวเลขที่จำเป็นต้องครบและเป็นค่าที่อ่านได้
- ผู้เซ็นต้องกรอกชื่อและตำแหน่ง
- ชื่อและตำแหน่งใช้ดรอปดาวน์ มีส่วนจัดการรายชื่อเพื่อเพิ่มภายหลัง ไม่ใส่รายชื่อบุคคลสมมติให้เป็นรายชื่อจริง
- จำค่าที่เลือกแยกแต่ละบทบาทผู้เซ็นในเบราว์เซอร์เดิม จนกว่าจะเลือกคนหรือตำแหน่งใหม่
- ล้างข้อมูลหรือเริ่มบันทึกใหม่ต้องคงชื่อและตำแหน่งที่เลือกไว้ แต่ล้างลายเซ็นของเอกสารเดิม
- เอกสารที่ล็อกต้องไม่เปลี่ยนชื่อ/ตำแหน่งตามค่าเริ่มต้นของผู้ใช้อื่น
- ในฟอร์มเทอร์ไบน์ เงื่อนไขปัจจุบันคือ 624 ช่องและข้อมูลหัวฟอร์ม ไม่ได้บังคับภาพ/QR/GPS ครบทุกชั่วโมง การบังคับหลักฐานต้องกำหนดเพิ่มให้ชัดเจนก่อนใช้งานจริง

### 5.2 ลำดับในฟอร์มตัวอย่าง

1. ผู้บันทึกกะ 1 และ 2 เซ็นให้ครบ ภายในขั้นนี้เซ็นคนไหนก่อนก็ได้
2. หัวหน้ากะ 1 และ 2 จึงเซ็นได้ ภายในขั้นนี้เซ็นคนไหนก่อนก็ได้
3. ผู้รับรองการตรวจสอบ / หัวหน้าแผนก เซ็นเป็นขั้นสุดท้าย

ตรวจเงื่อนไขทั้งก่อนเปิดหน้าเซ็นและก่อนยืนยัน ไม่ใช่ปิดปุ่มอย่างเดียว หากลบหรือแทนที่ลายเซ็นขั้นก่อนหน้า ต้องล้างการรับรองที่พึ่งพาลายเซ็นนั้นในขั้นถัดไป

### 5.3 รูปแบบหน้าเซ็นและกรอบแสดงผล

- หน้าเขียนลายเซ็นเต็มพื้นที่จอ พร้อมตารางเส้นบางเป็นไกด์
- ความหนาเส้นปรับให้เหมาะกับพื้นที่เขียนและขนาดแสดงผล
- กรอบแสดงลายเซ็นมีขนาดกระชับ ไม่ต้องใหญ่เท่าหน้าเขียน
- ชื่อและตำแหน่งอยู่บรรทัดเดียวกันตรงกลางใต้ลายเซ็น
- วันที่และเวลาไทยถึงวินาทีอยู่ภายในกรอบ พร้อม GPS และค่าความแม่นยำ
- บันทึกเวลาเมื่อยืนยัน และไม่เปลี่ยนเวลานี้เมื่อเปิดฟอร์มหรือพิมพ์ใหม่
- ช่องที่ยังรอขั้นก่อนหน้าแสดงข้อความรอเป็นสีแดง อีกบรรทัดใต้ “ยังไม่ได้เซ็นชื่อ” ภายในกรอบ
- เก็บลายเซ็นเป็นเส้นพิกัดที่ปรับสัดส่วนได้ เพื่อวาดใหม่ได้คมชัด
- งานพิมพ์วาดเส้นลายเซ็นโดยตรงเป็นสีดำและหนาพออ่าน ไม่ย่อภาพทั้งกรอบจนชื่อ/เวลาหรือเส้นเล็กเกินไป
- สามารถเอาเส้นไกด์ออกจากลายเซ็นที่พิมพ์เพื่อให้อ่านชัด
- การปิดเมนูคัดลอก/ลากภาพเป็นเพียงการลดการคัดลอกทั่วไป ไม่รับประกันป้องกันภาพหน้าจอหรือการแก้ไฟล์

## 6. ล็อกและปลดล็อกเอกสาร

- เซ็นครบทุกบทบาทแล้ว ล็อกข้อมูล ลายเซ็น และหลักฐานตรวจ
- เอกสารล็อกยังดูชั่วโมงต่าง ๆ พิมพ์ และส่งออกได้
- ปิดการนำเข้าทับ ล้างฟอร์ม และลบ/เซ็นทับขณะล็อก
- เปิดฟอร์มใหม่หรือนำเข้าข้อมูลที่เซ็นครบ ต้องรักษาสถานะล็อก
- มีปุ่มปลดล็อกเพื่อแก้ไข สำหรับ Demo ใช้รหัส **1234**
- รหัสผิดต้องไม่ปลดล็อก รหัสไม่บันทึกลง JSON หรือ PDF
- เมื่อปลดล็อก เก็บค่าที่กรอก แต่ล้างลายเซ็นทั้งชุดให้เซ็นรับรองใหม่ หลังเซ็นครบจะล็อกอีกครั้ง
- รหัส Demo ใน HTML ไม่ใช่ระบบยืนยันสิทธิ์ที่ปลอดภัยสำหรับงานจริง
- ระบบจริงควรเก็บฉบับเดิม ประวัติแก้ไข เหตุผล ผู้แก้ และใช้บัญชี/สิทธิ์บนเซิร์ฟเวอร์

## 7. หลักฐานตรวจรายชั่วโมง

ขั้นตอน: เลือกเวลา → ยืนยันเครื่อง → ถ่ายภาพค่าที่อ่าน → กรอกค่า → เก็บ GPS → บันทึก

- สแกน QR ด้วยกล้อง และตรวจว่ารหัสตรงกับเครื่องในฟอร์ม
- ถ้ากรอกรหัสเอง ให้แสดงว่า “กรอกเอง” ห้ามแสดงเป็น “สแกน QR”
- ภาพหลักฐานถ่ายจากกล้องให้เห็นตัวเลขบนจอ/เกจและระบุเครื่องได้
- เก็บภาพ รหัสเครื่อง และเวลาถ่ายแยกแต่ละชั่วโมง
- เก็บ GPS ใหม่ พร้อมความแม่นยำและเวลาเก็บพิกัด
- GPS ถูกปฏิเสธ หมดเวลา ไม่พบตำแหน่ง หรือไม่รองรับ ต้องแสดงสถานะจริง ห้ามใส่พิกัดตัวอย่างแทน
- ลายเซ็นเดิมที่ไม่มี GPS ต้องแสดงว่าไม่ได้บันทึก ไม่เติมพิกัดย้อนหลัง
- กล้องต้องหยุดทำงานเมื่อปิดหน้ากล้อง
- เปลี่ยนรหัสเครื่องแล้วหลักฐานเดิมอาจไม่ตรง ต้องถามก่อนล้างและแจ้งให้สำรองข้อมูล
- แสดง “หลักฐานครบ / บางส่วน / ไม่มีหลักฐาน” แยกจากจำนวนช่องตัวเลข
- กล้องและ GPS ขึ้นกับการอนุญาตของอุปกรณ์และบริบทเว็บที่รองรับ โดยงานจริงควรเปิดผ่าน HTTPS
- GPS, QR และภาพเพียงอย่างเดียวไม่พิสูจน์ว่าตรวจจริง 100% ต้องมีผู้ตรวจทานและระบบตรวจย้อนหลัง

## 8. พิมพ์และ PDF

- แยกปุ่ม **บันทึก PDF** ซึ่งดาวน์โหลดไฟล์โดยตรง ออกจากปุ่ม **พิมพ์** ซึ่งเปิดหน้าต่างเครื่องพิมพ์
- ฟอร์มตัวอย่างใช้ A4 แนวนอน หน้าเดียว มีตารางครบ 24 ชั่วโมง ลายเซ็นครบ และรหัสท้ายเอกสาร
- ใช้ขนาดกระดาษเดียวกับที่กำหนด ไม่ปล่อยท้ายเอกสารข้ามหน้า
- รักษารูปแบบต้นฉบับทั้งหมด ยกเว้นส่วนลายเซ็นที่อนุญาตให้ออกแบบใหม่
- ใช้ตัวสร้างเอกสารร่วมกันสำหรับพิมพ์และ PDF เพื่อลดความต่าง
- หากใช้ภาพต้นฉบับเป็นพื้นหลัง ต้องใช้ความละเอียดเพียงพอ วางข้อมูลตรงช่อง และไม่แก้ต้นฉบับ
- ฟอร์มที่เปิดผ่าน `file://` ต้องทดสอบว่าภาพ/ฟอนต์ไม่ทำให้ Canvas ส่งออกไม่ได้ ใช้ทรัพยากรฝังหรือวิธีที่รองรับ
- การใช้ PDF แบบภาพทำให้คัดข้อความใน PDF ไม่ได้ ควรเก็บ JSON/CSV สำหรับวิเคราะห์ข้อมูล
- ก่อนส่งมอบ ให้ทดสอบทั้งเอกสารว่าง ข้อมูลครบ และลายเซ็นครบ แล้วเปิด PDF ตรวจจำนวนหน้าและภาพจริง

## 9. บันทึกข้อมูลและเตรียม Dashboard

| รูปแบบ | การใช้งาน |
|---|---|
| ข้อมูลในเบราว์เซอร์ | เปิดกลับมาแก้ไขในเครื่อง/เบราว์เซอร์เดิม |
| JSON | สำรองข้อมูลครบ รวมค่าตรวจ ลายเซ็น ภาพ และ GPS |
| CSV | วิเคราะห์ค่าตรวจใน Excel / Power BI |
| PDF | เอกสารอ่านและพิมพ์ ไม่ใช่ข้อมูลหลักสำหรับ Dashboard |

- ใช้รหัสแบบฟอร์มและรุ่นโครงสร้างข้อมูล เพื่อรับไฟล์เก่าได้อย่างถูกต้อง
- ตรวจข้อมูลนำเข้าทั้งค่าตรวจ ลายเซ็น พิกัด และภาพก่อนแทนที่ข้อมูลปัจจุบัน
- บันทึกไม่สำเร็จหรือพื้นที่เบราว์เซอร์เต็มต้องแจ้ง ไม่แสดงว่าเก็บสำเร็จ
- CSV ปัจจุบันมีหัวเอกสารนำหน้าตาราง หากจะรวมหลายเอกสารทำ Dashboard ให้แปลงเป็นหนึ่งแถวต่อเครื่อง/วัน/เวลา
- โครงสร้างที่แนะนำ: `รหัสฟอร์ม | วันที่ตรวจ | เวลาตรวจ | รหัสเครื่อง | ปีการผลิต | ค่าตรวจ… | สถานะหลักฐาน | สถานะรับรอง`
- เวลาอุปกรณ์กับเวลาที่เซิร์ฟเวอร์รับข้อมูลต้องแยกกันเมื่อเพิ่มระบบกลาง

## 10. Data Center เฉพาะเอกสารบันทึก

- หน้าตัวอย่างคือ `data-center.html` ให้เริ่มเฉพาะคลังเอกสารบันทึก ไม่ขยายระบบอื่นโดยไม่ตกลง
- มีปุ่มเพิ่มแบบฟอร์มจาก HTML ที่สร้างไว้แล้ว
- ระบุชื่อแบบฟอร์ม รหัสเอกสาร และแผนก
- มีค้นหา กรองแผนก เปิดแบบฟอร์ม ดาวน์โหลด HTML และนำออกจากคลัง
- สำรองและกู้คืนคลังเป็น JSON
- คลังปัจจุบันใช้ IndexedDB ในเบราว์เซอร์ ไม่ได้เป็นฐานข้อมูลรวมหลายอุปกรณ์
- การนำฟอร์มออกจากคลังไม่ควรลบผลบันทึกของฟอร์มนั้น
- HTML ที่นำเข้าเปิดใช้สคริปต์ได้ ให้เพิ่มเฉพาะไฟล์ที่เชื่อถือ
- ฟอร์มที่แจกจ่ายผ่าน HTML ไฟล์เดียวควรฝัง CSS/JS/ภาพ/ฟอนต์ หรือมีชุดไฟล์ประกอบที่หาได้ครบ
- ห้ามถือว่าการเพิ่ม HTML จะนำผลบันทึกเข้าสู่ Data Center โดยอัตโนมัติ ต้องกำหนดวิธีรับข้อมูลกลางเพิ่มเติม

## 11. การใช้ข้อมูล Demo

- มีปุ่มกรอกตัวเลข Demo พร้อมยืนยันก่อนแทนที่ข้อมูลเดิม
- ข้อมูลตัวอย่างต้องครบตามโครงสร้างของฟอร์ม และแสดงป้าย DEMO บนหน้าเว็บและเอกสาร
- ตัวเลข Demo ต้องไม่ถูกนำไปสรุปเป็นผลตรวจจริง
- ไม่สร้างลายเซ็น ภาพตรวจ QR หรือ GPS ปลอม
- ไม่เขียนทับข้อมูลที่ผู้ใช้เก็บไว้โดยอัตโนมัติ
- ควรยกเลิกการกรอก Demo อัตโนมัติเมื่อเปลี่ยนจากการสาธิตไปใช้งานจริง

## 12. ขั้นตอนสร้างแบบฟอร์มใหม่

1. อ่านต้นฉบับและทำรายการช่อง/ค่าควบคุม/รอบตรวจ/ผู้เซ็น
2. ยืนยันข้อมูลที่อ่านไม่ชัดและเงื่อนไขช่องจำเป็น
3. สร้างหน้ากรอกแบบแบ่งรอบและกลุ่มข้อมูล พร้อมสถานะความครบ
4. เพิ่มบันทึกอัตโนมัติ นำเข้า/ส่งออก JSON และ CSV
5. เพิ่มหลักฐานตามระดับที่ตกลง พร้อมสถานะเมื่ออุปกรณ์ไม่รองรับ
6. เพิ่มเงื่อนไขก่อนเซ็น ลำดับรับรอง และล็อกหลังเซ็นครบ
7. สร้างงานพิมพ์/PDF ตามเทมเพลต โดยจัดส่วนลายเซ็นให้ชัด
8. ตรวจมือถือ แท็บเล็ต ฟอนต์ และการใช้งานออฟไลน์
9. ตรวจบันทึกแล้วเปิดใหม่ นำเข้ารุ่นเก่า และส่งออกข้อมูล
10. เพิ่มฟอร์มเข้า Data Center พร้อมชุดไฟล์ที่ใช้ครบ
11. บันทึกสิ่งที่ทดสอบ ข้อจำกัด และขั้นตอนเปิดใช้งาน
