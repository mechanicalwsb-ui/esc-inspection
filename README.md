# ESC Machine Inspection Center — v3.0.1

ระบบตรวจเครื่องจักร สายเดินตรวจร่วมกัน และติดตามงานซ่อมของ ESC รองรับโหมดเซิร์ฟเวอร์และโหมดเปิดไฟล์ตรง

## แบบบันทึกจากเอกสารจริงแผนกลูกหีบ

เปิดเมนู **แบบฟอร์ม** แล้วกด **ฟอร์มจากเอกสารจริงแผนกลูกหีบ** หรือเปิด `/source-forms.html` บนเซิร์ฟเวอร์ โหมดเปิดไฟล์ใช้ `public/source-forms.html`

- คลังเอกสาร 59 ไฟล์: PDF 56 ไฟล์และ Excel 3 ไฟล์ เปิดต้นฉบับและอ่านข้อความได้ โดยระบบอ่านไฟล์ต้นฉบับเท่านั้น
- แบบบันทึก 39 แบบ: ใบตรวจเครื่องมือ 18 แบบและบันทึกเครื่องจักร/การเดินเครื่อง/การผลิต 21 แบบ อีก 20 ไฟล์ใช้เปิดดูอ้างอิง รวมใบอนุญาตทำงานและทะเบียนเอกสาร
- กรอกวันที่ เครื่อง/พื้นที่ กะ ปีการผลิต แล้วเพิ่มรายการตามเวลา/จุดตรวจ เลือกผลตรวจหรือกรอกค่าที่วัดจริง ไม่คำนวณค่าปกติให้เอง
- เก็บแบบร่างอัตโนมัติใน IndexedDB ของเบราว์เซอร์ บันทึกเข้า SQLite ด้วยบัญชีที่ล็อกอิน หรือบันทึกในเครื่องเมื่อเปิดไฟล์ตรง พิมพ์และส่งออก CSV ได้
- ผลบันทึกเก็บแยกใน `source_form_records` พร้อมผู้บันทึก เวลา SHA-256 ของเอกสารและสำเนาโครงสร้างฟอร์ม ไม่เขียนทับเอกสารต้นฉบับ ผลเดิมเปิดดูได้อย่างเดียว
- โหมดเซิร์ฟเวอร์ต้องออนไลน์ขณะเปิดหน้านี้และส่งผลบันทึก หากการส่งขาดตอน แบบร่างถูกเก็บไว้และส่งคำขอเดิมอีกครั้งได้โดยไม่สร้างผลซ้ำ หากกำลังออฟไลน์ให้เก็บแบบร่างไว้แล้วส่งเมื่อกลับมาออนไลน์
- ใบแบบบันทึกนี้ยังไม่แทนลายเซ็นอนุมัติจากหัวหน้างาน และไม่เปลี่ยนสถานะสุขภาพเครื่อง/สร้างใบซ่อมอัตโนมัติ ใช้หน้าใบตรวจหลักสำหรับกระบวนการนั้น
- เครื่อง/จุดตรวจที่มีหลายชุดให้เพิ่มรายการแยกตามจุด โดยเฉพาะ ML-03, ML-10, ML-11, ML-12 และ ML-15 ช่องวัด/ค่าควบคุมของ ML-12 และ ML-15 กรอกตามรายการในต้นฉบับ
- เซิร์ฟเวอร์อ่านต้นฉบับจากโฟลเดอร์ที่ผู้ใช้ระบุ หากย้ายเซิร์ฟเวอร์ให้ตั้ง `COMIS_SOURCE_DOCUMENTS` เป็นที่ตั้งโฟลเดอร์ต้นฉบับ ไม่ใช้ API ใดเขียนไฟล์ในโฟลเดอร์นั้น

รายการต้นแบบอยู่ใน `public/assets/source-forms/catalogue.js`; การอ่านทบทวนและค่า SHA-256 อยู่ใน `logs/source-form-review/manifest.json` ใช้ `src/build-source-catalogue.py` สร้างคลังใหม่จากเอกสาร โดยสคริปต์อ่านต้นฉบับอย่างเดียวและเขียนผลไว้ในโปรเจกต์นี้

## เริ่มใช้งาน

1. ใช้ Node.js 22.13 ขึ้นไป แนะนำ Node.js 24 LTS
2. เปิด Terminal ที่โฟลเดอร์โปรเจกต์แล้วรัน `node --no-warnings server.js`
3. เปิด `http://localhost:3000` จากเครื่องเซิร์ฟเวอร์ และตั้งรหัสผ่านผู้ดูแลครั้งแรก (10–128 ตัวอักษร)
4. บัญชีผู้ดูแลเดิมใช้รหัสพนักงาน `EMP-1001` ระบบไม่สร้างรหัสผ่านเริ่มต้นให้
5. ในหน้า **ผู้ใช้งาน & ตั้งค่าระบบ** เลือกแก้ไขผู้ใช้ แล้วกด **ตั้งรหัสผ่านชั่วคราว** ผู้ใช้ต้องเปลี่ยนรหัสผ่านก่อนเริ่มงาน
6. ใช้บัญชีของตนเองในการตรวจ ระบบล็อกชื่อผู้ทำรายการตามบัญชีที่เข้าสู่ระบบ

การตั้งรหัสผ่านผู้ดูแลครั้งแรกทำได้จาก loopback ของเครื่องเซิร์ฟเวอร์เท่านั้น โหมด `file://` เป็นข้อมูลเฉพาะเครื่อง ไม่มีการรับรองตัวตนหรือส่งเข้า SQLite

## ออฟไลน์และการตรวจร่วมกัน

- โหลดเว็บออนไลน์อย่างน้อยหนึ่งครั้งเพื่อเก็บไฟล์และข้อมูลล่าสุดก่อนออกหน้างาน
- ใบตรวจและแบบร่างร่วมที่ส่งไม่ได้จะเก็บใน **IndexedDB** พร้อมรหัสคำขอ ไม่สร้างใบตรวจหรือใบซ่อมกลางจนกว่าจะส่งสำเร็จ
- แถบด้านบนแสดงจำนวน **รอส่ง** และ **ต้องตรวจแก้** เมื่อเครือข่ายกลับ ระบบลองส่งอัตโนมัติด้วยบัญชีเจ้าของรายการ
- ข้อผิดพลาด 4xx/5xx จาก API ไม่เปลี่ยนไปบันทึก LocalStorage และไม่แจ้งว่าสำเร็จ
- กรณีข้อมูลชนกัน เปิด **รายการรอส่ง → ตรวจและแก้รายการ** โหลดข้อมูลล่าสุด แล้วรวมคำตอบก่อนบันทึก สามารถดาวน์โหลด JSON ของรายการค้างได้
- การรีเฟรชข้อมูลร่วมทำทุก 15 วินาทีเมื่อหน้าเว็บเปิดอยู่ รักษาข้อมูลที่กำลังกรอก และตรวจ revision ก่อนเขียนเพื่อป้องกันการทับคำตอบผู้อื่น
- ตรวจฉุกเฉินเป็นการตรวจบางส่วน จึงไม่ทำให้จุดในสายตรวจครบฟอร์มโดยอัตโนมัติ
- ปุ่มผ่านข้อสังเกตทั้งหมดไม่สร้างค่าตัวเลขให้เอง ค่าตัวเลขต้องกรอกจากการวัด ข้อที่วัดเฉพาะขณะเดินเครื่องจะบันทึกเป็น `na` เมื่อเครื่องหยุด
- โหมดเปิด `index.html` โดยตรงใช้ IndexedDB คนละชุดกับฐานกลาง ย้าย LocalStorage เดิมเข้ามาและเก็บต้นฉบับเดิมไว้ ไม่มีการส่งข้อมูลโหมดนี้เข้าฐานกลางอัตโนมัติ

## QR และการใช้มือถือ

ป้าย QR ใช้รูปแบบ `ESC:MACHINE:<รหัสเครื่อง>` กล้องในเว็บอ่าน QR แล้วเปิดเครื่องที่ตรงกัน รองรับป้าย URL เดิมที่มี `inspect_machine` ด้วย มีช่องกรอกรหัสและรายการเลือกเครื่องเป็นทางเลือก

กล้องและ Service Worker บนอุปกรณ์ผ่าน LAN ต้องใช้ **HTTPS** ที่อุปกรณ์เชื่อถือ `localhost` ใช้กล้องได้บนเครื่องเซิร์ฟเวอร์ การทดสอบอัตโนมัติครอบคลุมการถอดรหัส QR และกรอกรหัส แต่ยังต้องทดสอบสิทธิ์กล้องและการโฟกัสด้วยมือถือ/iPad จริง

เซิร์ฟเวอร์รองรับ TLS โดยกำหนด `COMIS_TLS_CERT` และ `COMIS_TLS_KEY` เป็นพาธไฟล์ certificate/key ที่เตรียมไว้ก่อนรัน ไม่ได้สร้างหรือติดตั้ง certificate ให้เอง

## สำรองและกู้คืน

- เมื่อเริ่มเซิร์ฟเวอร์ ระบบสร้างสำรองของวันนั้น และตรวจทุกชั่วโมงว่ามีสำรองสำหรับวันใหม่หรือยัง
- สำรองอยู่ใน `data/backups` และตรวจ `PRAGMA integrity_check` ทุกไฟล์ ไม่ลบสำรองเก่าอัตโนมัติ
- สำรองเอง: `node --no-warnings src/backup-cli.js backup`
- ตรวจสำรอง: `node --no-warnings src/backup-cli.js check "พาธสำรอง.db"`
- กู้คืน: **หยุดเซิร์ฟเวอร์ก่อน** แล้วรัน `node --no-warnings src/backup-cli.js restore "พาธสำรอง.db" --server-stopped` ระบบเก็บสำรองฐานเดิมก่อนแทนที่
- Undo ย้อนเฉพาะแถวที่เปลี่ยนและปฏิเสธหากมีคนแก้ต่อ รายการเก่าที่มีเฉพาะ Snapshot ทั้งฐานถูกปิดการย้อนเพื่อป้องกันทับงานภายหลัง
- SQLite ยังคงใช้ `journal_mode=DELETE` สำหรับโฟลเดอร์ OneDrive ไม่ควรเปิดฐานเดียวกันจากเซิร์ฟเวอร์หลายเครื่องพร้อมกัน

## ทดสอบ

`node --no-warnings --test tests/system.test.js` ใช้ฐานข้อมูลชั่วคราวแยกจาก `data/comis.db`

`tests/browser-check.js` ใช้ Playwright และ Edge/Chrome ที่ติดตั้งอยู่ กำหนด `NODE_PATH` ให้ชี้แพ็กเกจ Playwright และ `COMIS_BROWSER_PATH` เมื่อใช้เบราว์เซอร์คนละพาธ การรันทดสอบไม่ตั้งรหัสผ่านหรือแก้ข้อมูลจริง

## การอัปเดตและขอบเขต

ไลบรารี ฟอนต์ โลโก้ และสไตล์โหลดจากไฟล์ในโปรเจกต์ Tailwind 3.4.17 ทำงานจาก bundle ภายในเครื่อง เมื่อแก้ไฟล์เว็บในรุ่นถัดไปต้องเปลี่ยนชื่อ cache ใน `public/sw.js` ให้ตรงกับรุ่น เพื่อไม่ให้โค้ดต่างรุ่นปะปน

การแจ้ง Telegram ทดสอบได้เมื่อผู้ดูแลตั้ง Token/Chat ID จริง งานนี้ไม่ได้ส่งข้อความทดสอบไปยังบุคคลใด และไม่ได้ deploy ระบบ production
